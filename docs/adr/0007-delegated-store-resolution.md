# Store resolution delegates to an external command, opt-in

[Issue #73](https://github.com/sripwoud/pi-memsearch/issues/73) reported pi's memories splitting from Claude Code's: in a linked worktree and outside any git repo, the two sides resolve different stores and different collections, so the README's "pi recalls what Claude Code learned yesterday" quietly stops holding. The obvious fix — derive the project directory from `git rev-parse --git-common-dir` so every worktree shares the primary checkout's store — is the wrong one here. Upstream's stock plugin shell uses `git rev-parse --show-toplevel`, which returns the worktree, exactly what pi's `.git`-existence walk already returns. pi conforms to the mesh today; changing the derivation unconditionally would break parity with every stock plugin and mirror the same split back onto anyone not running the patched shell (ADR 0001). The split in the report comes from a locally modified plugin, and the durable fix for it belongs upstream.

So pi grows a seam instead of a policy. `PI_MEMSEARCH_STORE_CMD` names a command that owns the store and collection derivations, and optionally the index-state directory too. Unset — the default, and what the mesh sees — every store and collection resolution is byte-for-byte what it was.

Concretely:

- **Three modes, one command.** `<cmd> memory-dir` prints the absolute memory store directory; `<cmd> collection` prints the collection name; `<cmd> state-dir` prints the absolute index-state directory. All three run with the working directory set to the directory being resolved, so the command sees the same cwd pi does and needs no arguments.
- **Fail fast, never fall back.** A non-zero exit, empty output, or a relative path raises an error naming the command and the mode. Silently reverting to internal derivation would write memory to the wrong store, and a wrong store is worse than a stopped session. `state-dir` alone may print nothing on exit 0, which is how a resolver declines the mode (below).
- **The command outranks `MEMSEARCH_DIR`.** It is a deliberate pi-level opt-in; `MEMSEARCH_DIR` can arrive by inheritance from a mesh agent that repurposes it as an index-state directory.
- **Collection names come from the command.** pi never re-derives a name for a directory the command has answered for — including cross-repo fan-out and project-targeted expansion, each asking about its own target directory.
- **One subprocess per directory per mode, per process.** Answers are memoized for the life of the process, `state-dir` included. Capture, the indexer, every tool call and auto-context all resolve scope; without memoization that is a subprocess per resolution.
- **Only compaction needs a leaf `memory` store.** This started as a store-wide expectation. [#77](https://github.com/sripwoud/pi-memsearch/issues/77) showed it was wrong. A central store keyed per repo lays out as `<store-root>/<project>/`, holding day files directly, so no `<X>` has the store as its `memory` child. Index state therefore stops deriving from the store's parent. It reads the command's `state-dir` answer when there is one, else `$MEMSEARCH_DIR/.index-state.json` whenever that variable is set — memsearch's own state-dir override, and where its child writes the file (`index_state.py`) — else `dirname(memoryDir)`. A relative `MEMSEARCH_DIR` resolves at the repository directory, where that child runs.

  Compaction cannot follow. memsearch appends the summary to `<output dir>/memory/<date>.md`. For a store not named `memory`, that lands in a directory shared by every sibling project, outside the store it summarizes. So `memory_compact` refuses on such a store, naming it. Losing compaction there is a smaller loss than writing summaries to the wrong directory, and the refusal lifts if memsearch grows an `-o` that names the store directly.
- **A resolver answering outside a `.memsearch` tree names its state directory through the command, not through the environment.** memsearch writes `.index-state.json` only when the indexed path sits inside a `.memsearch` tree, or when `MEMSEARCH_DIR` is set (`index_state.py`). A store command answering with a path outside any such tree gets no state file written at all, so pi has nothing to read and `memory_status` reports no index health.

  A static `MEMSEARCH_DIR` export cannot fix this ([#89](https://github.com/sripwoud/pi-memsearch/issues/89)). A resolver keying state per collection has a different answer per repository, and one exported value cannot hold them all. Only something evaluated per directory can — which is what the store command already is. So `state-dir` is the third mode, and pi exports its answer as `MEMSEARCH_DIR` to the memsearch children it spawns, above any `MEMSEARCH_DIR` it inherited. The resolver still chooses the value; pi only carries it to the child that needs it, and sets no policy of its own. Index state is read back from the same answer.

  The mode is optional, and the opt-out is exit 0 printing nothing: a resolver that does not implement it behaves exactly as before, no error, index state falling back to `MEMSEARCH_DIR` and then to `dirname(memoryDir)`. Anything else — a non-zero exit, a relative path — fails fast like `memory-dir`, because a half-answered state directory is a wrong one. A `case` with no default arm, the shape a resolver already has for two modes, declines correctly by construction.

- **Cross-repo discovery learned a second store shape, and not as part of the opt-in.** A scanned directory counted as a project only when it held `<dir>/.memsearch/memory`; `<dir>/memory` — the shape `MEMSEARCH_DIR` itself implies — now counts too, whether or not the command is set. Fan-out over a store that sits outside the repos found nothing otherwise. This widens what counts as a project by one directory name, which is mesh-conformant on its own merit; it is the one part of this change visible with the variable unset.
- **Fan-out asks the command about store directories.** Discovered projects are the directories holding the stores, so a resolver must answer for a store it is standing in. The current project is exempt — its leg reuses the collection already resolved at the session's own directory, so `scope: "all"` and `scope: "project"` can never disagree about where the current project's memory lives.
- **The repository directory is untouched.** memsearch child processes still run at the git root of the session's directory, so a project `.memsearch.toml` layers as it would for a CLI run there — the same split an absolute `MEMSEARCH_DIR` has. ([#91](https://github.com/sripwoud/pi-memsearch/issues/91) later closed the relative case: a relative override resolves at the repository directory for the store too, so only an absolute one still splits.)

Considered alternatives:

- **A store-root variable** that maps repo paths to a directory layout internally: rejected. Deciding that memory for `<repo>` lives at `<root>/<repo basename>` is store-routing policy, and it hardcodes one deployment's directory scheme inside a package other people install.
- **A key in the shared `~/.memsearch/config.toml`**: the better endgame, the wrong first move. It claims a name inside a file upstream owns. If upstream later adds a key of the same name with different semantics, every agent reading that file gets a silent collision.
- **Changing the default derivation to `--git-common-dir`**: deferred, not rejected. With delegation, a central store is reachable without it. It lands as a small follow-up if the upstream plugin-shell change merges, at which point every mesh agent moves together.

Reversal clause, following the precedent set for the sidecar (ADR 0005) and the transcript parser (ADR 0006): if upstream grows its own store-resolution hook, pi honors that hook and this variable degrades to an override. The endgame is to propose the same seam upstream as a plugin-shell convention, after which the external resolver becomes mesh configuration rather than a local patch.
