# Per-session warm sidecar for auto-context: hold the embedder, borrow the lock

[Issue #23](https://github.com/sripwoud/pi-memsearch/issues/23) deferred per-turn semantic injection on a warm-sidecar design: every memsearch CLI call pays ~3.4 s of uvx startup, Python import, and ONNX model load — unacceptable per prompt. Source reading (memsearch 0.4.17, milvus-lite 3.x) split that cost into two separable parts. The embedding model is the expensive one (~1.5–2 s load, ~0.7–1.0 GB resident) and has zero Milvus coupling — `memsearch.embeddings.get_provider` is a standalone seam whose output feeds `MilvusStore.search` directly. The store is the cheap one (tens to low hundreds of ms to open; milvus-lite 3.x runs in-process, no subprocess) but is guarded by an flock on the whole `~/.memsearch/milvus.db` directory — every collection, every project, machine-wide. The design follows the split: hold the embedder warm for the session, borrow the lock for milliseconds per prompt.

Concretely:

- **Per-session child process.** Spawned eagerly at `session_start` (`uv run` with the pinned `MEMSEARCH_SPEC`), JSON over stdio, exits on stdin EOF — no pidfiles, no discovery, no version skew, no orphans by construction. Warmup overlaps the user typing their first prompt.
- **Throwaway store per prompt.** Query embed and `MilvusStore` open run concurrently; one `hybrid_search` against the real project collection; `close()`. Lock contention → skip this prompt, no retry, never block. Same collection, same hybrid dense+BM25 scoring as `memory_search`, chunk hashes that chain into `memory_expand` — pi stays a smarter reader, never a divergent writer (ADR 0003).
- **300 ms hard cap, all providers.** Miss → no injection; the prompt never waits on memory. Remote embedding providers will miss often; documented limitation, not special-cased — bootstrap defaults the mesh to onnx, so local is the common case.
- **Injection is a persistent `CustomMessage`** returned from `before_agent_start` (`customType: memsearch-auto-context`, `display: false`), appended after the cached prefix where the new user prompt already invalidates — prefix-cache impact is nil and the byte-stable snapshot (system prompt) is untouched. Content: one preamble line, then at most 3 chunks in `memory_search` format (score, chunk_hash, source:lines), score floor 0.5, ~2000-char budget, chunks already verbatim in the stable snapshot dropped, no message at all when nothing clears the bar.
- **Query is the raw user prompt**, truncated (~500 chars). No LLM distillation on the prompt path.
- **Failure degrades to silence.** Any sidecar failure → no injection for that prompt; lazy respawn capped at 2 per session; 3 consecutive timeouts count as a crash; past the cap, auto-context is off for the session and `memory_status` says so (state, resolved provider/model, prompts/injected/skipped counters, last latency).
- **Freshness rides the indexer.** Entries written mid-session become injectable after the background reindex they already trigger; the stable snapshot owns very-recent memory, so auto-context's marginal value is the older tail. The indexer stays on the CLI in v1 — routing it through the sidecar is a follow-up once the sidecar is proven.
- **Config parity.** The sidecar resolves provider/model/uri/collection with `memsearch.config.resolve_config()` itself, cwd set to the project scope dir — byte-identical layering with the CLI (ADR 0001). The internals imports (`config`, `embeddings`, `store`) are guarded by the version pin plus a contract test that fails CI on a breaking bump.
- **Project-only, opt-in.** No cross-repo fan-out — ADR 0003 keeps that an explicit recall-tool escalation, and silently injecting other projects' memory every prompt would cross the line it drew. Enabled with `PI_MEMSEARCH_AUTO_CONTEXT=on`, off by default while the sidecar earns trust.

Considered alternatives:

- **Held-open store with idle release**: fastest per prompt, rejected — the flock is directory-wide, so holding it between prompts blocks every mesh agent's memory operation in every project on the machine, precisely during the idle windows when they run.
- **In-memory replica** (sidecar chunks and embeds the memory files itself, never touches Milvus): rejected — dense-only search diverges from the mesh's hybrid scoring and abandons the shared collection. Recorded as the contingency if real-world store-open times blow the 300 ms budget.
- **Stale-by-one prefetch** (no new process; a background CLI search fires after each exchange and injects at the next prompt): rejected — the injected context answers the previous prompt, so every topic change injects noise.
- **Per-machine daemon**: rejected — amortizes ~1 GB per concurrent session, which does not matter on the machines this runs on, at the price of socket/pidfile discovery, race-safe spawning, idle shutdown, cross-repo version-skew handling, and the orphan-process class memsearch's own plugins grew sweep code for. The stdio protocol does not care who is behind it; a daemon remains the escalation path if multi-session RAM ever becomes real.
- **Upstream serve mode**: deferred, not proposed — upstream explicitly positions against long-lived services ("no MCP servers, no sidecar services", verified 2026-08-15). Tracked in [#40](https://github.com/sripwoud/pi-memsearch/issues/40); if the stance shifts, this sidecar is the working prototype.
